## 〇、一页纸摘要（管理层只看这段）

`datakit` 是我们自己沉淀的**通用数据处理 SDK + 项目结构规范**，
把"**采集 → 描述性统计 → 清洗 → 校验 → 映射**"五步提炼成可复用的标准流程与目录契约。

它不是 demo，而是**已经在三个真实数据产品上跑通的生产底座**：

| 落地产物 | 规模 |
| --- | --- |
| 支撑的数据产品项目 | **3 个**（`project1_fdic_spatial` / `project2_fdic_survival` / `project6_spatial_teaching`） |
| 跑通的阶段实例 | **26 个**（9 + 9 + 8，含扩展阶段） |
| 累计处理原始数据 | **约 32.7 GB**（FDIC 1.58 GB + 教学四数据集 31.1 GB） |
| 代码规模 | SDK 13 个源文件 / **2,861 行**；测试 8 个文件 / 402 行 / **40 个用例** |

核心主张（一句话）：

> **数据项目的成本不在"跑通一次"，而在"别人接手、三个月后重跑、被质疑时自证"。
> `datakit` 把这三件事从"靠人自觉"变成"工程强制"。**

三条硬约束构成了它的差异化：

1. **只读源数据**——SDK 从不写回源文件，所有产出落到调用方指定的输出目录；
2. **每步都有报告**——机读（JSON/YAML）+ 人读（Markdown）各一份，全程可追溯、可审计；
3. **目的驱动**——空值 / 异常值的判定取决于字段「**角色**」（主键 vs 事件时间 vs 时变协变量…），
   不搞一刀切。

投入产出：**约 2,900 行代码 + 3 份规范文档**，换来了三个项目**统一的目录结构、
统一的报告契约、统一的降级策略**，以及一套新人可照抄的项目骨架。

## 一、产品概述

### 1.1 它是什么

`datakit` 由**三件套**组成，缺一不可：

| 组件 | 内容 | 解决什么 |
| --- | --- | --- |
| **SDK** | 13 个模块，五阶段 API + `Workflow` 编排 + `Project` 脚手架 | 把重复代码收进库里 |
| **规范 v2** | `PROJECT_STRUCTURE.md`（46 KB）+ `通用规范.md` + `DEVELOPMENT_GUIDE.md` | 把"项目该长什么样"写清楚，可评审 |
| **脚手架** | `datakit.project.Project`：阶段注册、`--stage` 单跑、`SUMMARY.md` 自动生成、`pipeline.log` | 把规范变成"照着做就行" |

支持的格式：**CSV/TSV、JSON/JSONL、XML、RDF、XLSX、gzip 包裹** 六大类。

### 1.2 为什么做

三个项目在 `datakit` 之前的状态是：根目录散落脚本（`step5_estimate.py` / `model.py` / `viz.py`），
**每个项目一套目录、一套命名、一套报告格式**。直接后果是：

- **交接成本高**：换人接手要先把"哪个脚本产出哪份数据"问一遍；
- **不可复现**：改了参数重跑，说不清两次结果的差异来自参数还是数据；
- **不可审计**：被问"这个数怎么来的"时，只能翻代码回答，没有产物级证据。

`datakit` 的切入点不是"更强的计算能力"，而是**"更强的可追溯性"**——
这是数据产品能否交付给客户、能否通过内控复核的真正门槛。

### 1.3 产品形态

```text
project_xxx/
├── README.md        # 立项六问（背景/创新点/数据可信度/可行性/运行/导航）
├── main.py          # 根编排：加载阶段，依次 run(project)
├── SUMMARY.md       # 自动生成：各阶段结论一页纸
├── datakit.yaml     # 项目元信息 + 扩展阶段登记
├── config/          # ★ 口径外置：改口径不改代码
├── 01_discover/ … 05_map/     # 内置五阶段（入口文件与目录同名）
├── 06_ … /                    # 扩展阶段（插件，blocking: false）
├── data_raw/        # 只读原始数据 + 数据说明书
└── logs/            # pipeline.log + stage_summaries.json
```

## 二、核心功能与亮点

### 2.1 功能一：五阶段统一契约（**报告即产物**）

| 阶段 | 模块 | 关键 API | 产物 |
| --- | --- | --- | --- |
| ① 采集 | `discover` | `scan` / `discover` | `Catalog`（清单 + **指纹** + 分组） |
| ② 描述性统计 | `profile` | `profile` / `detect_outliers` / `null_summary` | `Profile`（字段画像 + 异常值 + 空值） |
| ③ 清洗 | `clean` | `CleanPlan` / `clean` | `CleanResult`（数据 + **决策日志**） |
| ④ 校验 | `validate` | `validate` / `compare` | `ValidationReport` / `ComparisonReport` |
| ⑤ 映射 | `map` | `MappingScheme` / `map` | `MapResult`（数据 + 报告） |

**每个阶段必须产出机读 + 人读两份报告**——这是规范里的硬要求，不是建议。

### 2.2 功能二：**决策日志**（清洗不是黑箱）

清洗的每一步动作（为什么删、删了多少、用什么填）都写入 `DecisionLog`。
`project1` / `project2` 各自剔除 4.26% 的行（120,261 行），
但**"剔了什么、为什么剔、这批缺失是否随机"**在报告里是可查的——
这正是我们在汇报里敢主动写"缺失 100% 集中在 1994–2010，早年样本代表性弱"的底气。

### 2.3 功能三：**目的驱动**的空值/异常判定（8 种字段角色）

```python
Role.KEY            # 主键：缺失即数据缺陷，通常剔除
Role.EVENT          # 事件时间：缺失 = 右删失，是有意义信息，不是脏数据
Role.TIME_VARYING   # 时变协变量：缺失可标记/填充，不轻易删行
Role.SPATIAL        # 经纬度：需做边界/精度检查
Role.CATEGORICAL / NUMERIC / TARGET / IGNORE
```

> **为什么重要**：同样是"空值"，`SIMS_ACQUIRED_DATE`（关闭日期）为空意味着**网点还活着**，
> 删掉它就是**生存分析里最致命的错误**。`datakit` 用 `Role` 把这类判断**前置到配置里**，
> 而不是散落在各项目的 if-else 中。

### 2.4 功能四：扩展阶段插件机制（**让规范能长出新能力**）

内置五阶段之外的能力（建模 / 可视化 / 结论 / 交互展示）一律做成**扩展阶段**：

- 在 `datakit.yaml` 登记，暴露 `run(project) -> dict`；
- **`blocking: false`**：失败只降级告警，**不阻断主流程**——
  这是三个项目的交互展示层在缺 CSV 时仍能出产品的原因；
- 报告要求"减配但不许没有"：建模必须有 `metrics.json` + `replication_manifest.json`
  （版本 / 参数 / 随机种子 / **输入指纹**）——**没有 manifest = 不可复现 = 不算产出**。

> **沉淀路径已写死**（规范 §8.7）：扩展阶段被 **≥2 个项目复用**后，才升级为内核模块。
> 目前 `06_train`（p2）与 `06_visualize`（p1/p2/p6）已具备复用条件，**但尚未升级**——见 §5。

### 2.5 功能五：`config/` 口径外置（**改口径不改代码**）

字段角色与等级（必需 / 重要 / 可选 / 忽略）、业务规则、清洗计划全部落在 `config/*.yaml`。
业务口径变更（如"同业定义为同 BKCLASS"、"主环取 5 km"）**改 YAML，不改 Python**，
评审时只需看配置文件，不必读代码。

### 2.6 功能六：`Project` 脚手架——规范变成"照着做就行"

- 阶段注册与顺序执行、`--stage` 单阶段重跑、`--list` 阶段清单；
- 自动维护 `logs/pipeline.log` 与 `logs/stage_summaries.json`；
- **自动生成 `SUMMARY.md`**（各阶段状态 + 关键指标 + 一句话结论）——
  本系列四篇汇报稿里的大量数字，直接来自这个文件。

### 2.7 功能七：只读源数据（**安全边界**）

SDK **从不写回源文件**，不修改系统环境，不修改工作空间外文件。
1.58 GB 与 31.1 GB 的原始数据全程只读——这是能放心让新人跑流水线的前提。

### 2.8 功能八：三份规范文档（**可评审、可交接**）

| 文档 | 内容 |
| --- | --- |
| `PROJECT_STRUCTURE.md`（46 KB） | 目录结构、五阶段报告必须有什么、`config/` 归属、扩展阶段规范、**出图规范（选型/中文/落盘）**、README 规范 |
| `通用规范.md` | 设计原则、IO 契约、核心抽象、报告与日志契约、错误与异常、命名、**安全与边界** |
| `DEVELOPMENT_GUIDE.md` | 新增格式 / 清洗动作 / 映射操作 / 断言的标准步骤 + 开发检查清单 + 测试约定 |

### 4.2 已验证的落地证据（**不是"能跑"，是"真的在跑"**）

1. **可追溯**：三个项目共 26 个阶段，每个阶段都有机读 + 人读两份报告。
2. **可复现**：`project1` 的 `replication_manifest.json` 含版本 / 参数 / 随机种子 / 输入指纹；
   `project6` 的 4 份 `version_lock.json` 冻结了行数与库版本，
   **交互教材里"你能重跑出同样的数"这句承诺是被这几个文件支撑的**。
3. **可降级**：`project2` 与 `project6` 的展示层在**缺样本级 CSV** 时（受 `.gitignore` 约束不入库），
   自动降级为上游真实静态图并**显式披露**，从未为了"好看"画出编造的图。
4. **可交接**：四篇产品汇报稿的数字**直接来自 `SUMMARY.md` 与各阶段 JSON**，
   没有一处需要"问一下原作者"。

### 4.3 差异化（**明确它是什么、不是什么**）

| 对比对象 | `datakit` 的差异 |
| --- | --- |
| **直接写脚本** | 统一目录 / 命名 / 报告契约 + 决策日志；交接与复现成本从"靠人"变"靠工程" |
| **Airflow / dbt** | **不是替代品**。它们解决调度、依赖与数仓建模；`datakit` 面向**单机、研究型数据产品**，核心是**报告与决策日志**而非任务调度，零基础设施即可跑 |
| **pandas-profiling / ydata** | 它们只做**画像**；`datakit` 覆盖采集→清洗→校验→映射**全流程**，且**强制**产出决策日志与双份报告 |
| **内部临时工具** | 有规范文档与测试，可评审、可交接、可对外解释 |

### 4.4 已知短板（**必须随成果一起汇报**）

1. **测试覆盖不均**：`test_pipeline.py` **仅 1 个用例**，是全项目最薄的一环——
   而 `Workflow` / `Project` 恰是最核心的编排逻辑，风险最高。
2. **无 CLI**：新建项目仍要手工复制目录结构，规范落地依赖自觉。
3. **无 Parquet / 数据库 IO**：31 GB 级数据只能靠 CSV + 抽样，IO 是性能瓶颈之一。
4. **单机、无调度 / 并行 / 增量**：全量重跑 `project6` 成本高；`project1` 端到端约 26 分钟。
5. **API 未承诺稳定**：`v0.1.0`，三个项目共用同一份代码，**升级需同步回归**。
6. **schema 缺业务合理性规则**：`project6` 发现 `sz_bike` 的 (0,0) 空岛与
   lat=47.66/lon=132.54 的飞点——两者都通过了经纬度**几何范围**断言。
   **"合法"不等于"合理"，这条规则目前只能在下游裁切里兜，未进校验层。**
7. **模型 / 可视化能力尚未沉淀为内核**：`06_train`、`06_visualize`、`09_interactive`
   目前分散在各项目中，按规范 §8.7（**≥2 个项目复用才升级**）已具备条件，但**尚未升级**。

> 汇报建议：把第 1 条和第 7 条当作下一阶段的**首要工程项**，而不是"有空再说"。
