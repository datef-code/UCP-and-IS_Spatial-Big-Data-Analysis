## 〇、为什么要有 v2：v1 被判定为"汇报"而非"产品"

v1（`portal/` 现状）是九个介绍页面，**没有输入、没有计算、没有可交付输出**——
`portal/README.md` 自己写死了"不产出任何新的分析结论，也不做任何建模""无后端、无用户系统"。

更严重的是：三个视角的独立审查（产品 / 业务 / 面试官）指出，**把现有产物直接包装成产品会触发"包装反噬"**——
每一条写在 README 里的"已知限制"，都会变成"你明知有问题还拿它卖"的证据。

因此 v2 的设计前提不是"怎么讲得更好听"，而是：

> **产品的核心能力，必须是"判断一个结论能不能用、能用到什么程度"。**

这不是退而求其次，而是把唯一没有竞品的东西做成主菜。

## 一、设计前提与硬约束

### 1.1 环境约束（不可协商）

| 约束 | 来源 | 影响 |
|---|---|---|
| 不修改任何既有文件、不改动工作区外环境 | 用户指定 | 所有新增代码只能落在 `portal/` |
| 样本级与格级明细（`.csv`/`.parquet`/`.pkl`/`*/*/*/data`）**全部不入库** | 仓库根 `.gitignore` | **能真算的只有入库的 JSON/TXT/MD/YAML 里的系数与聚合值** |
| 需能离线打开 | 展示与交付场景 | 默认纯静态，`file://` 双击可开，不依赖 CDN |

### 1.2 由约束直接推出的三条设计原则

1. **能算的才算，不能算的显式降级**——不做"看起来能算其实在编"的功能（延续 v1 已确立的口径）。
2. **每个输出必须携带三件套**：点估计 + 不确定性 + **使用边界**（可用于 / 不可用于）。
3. **不修补硬伤就不上线对应功能**——见 §六。

## 二、产品定位（重新定义）

### 2.1 一句话

> **网点决策台**：把"关一家店，周边会发生什么"变成一个**能拿去开会、被质询时站得住**的答案——
> 因为它自带可信度等级、使用边界与证据来源。

### 2.2 定位的关键转变

| | 旧（v1 / 汇报口径） | 新（v2） |
|---|---|---|
| 卖什么 | 我们的分析结论 | **一套判断"结论能不能用"的方法 + 可交付的证据卡** |
| 主菜 | 结论数字（−5.26pp） | **强度分级 + 准入体检 + 敏感性诊断** |
| 对待限制 | 写在"已知限制"章节里 | **限制是产品功能**（止损条件自动触发并阻断误用） |
| 用户第一眼 | 我们多厉害 | **你的数据能不能做、能做的话能拿到什么等级** |

### 2.3 为什么这个定位能绕开 R2 结构性矛盾

审查发现的致命矛盾：**最好卖的市场（连锁零售）因为关店内生，大概率只能交付 C 级结论。**

v2 的解法不是回避，而是**把等级做成产品分层**：

- 准入体检在**第一周**就判定客户数据能支撑 A / B / C 哪一级；
- C 级不硬卖成 A 级，而是切换成交付物更轻、价格更低的**描述性评估产品**；
- 客户在**签约前**就知道自己能拿到什么——这本身就是差异化（"这家是真的懂"）。

**结构性矛盾从"卖不出去"变成"产品分层"。**

### 2.4 目标用户

| 优先级 | 岗位 | 说明 |
|---|---|---|
| P0 | 咨询 / 市场研究机构的项目经理与量化分析师 | 决策链短、有外包预算科目、要求白标与可审计（本仓库强项） |
| P0 | 连锁零售/餐饮/药店的**网络规划经理**、选址拓展经理 | 自己有门店数据，缺方法；但**需先过准入体检** |
| P1 | 银行网点网络优化岗、并购整合 PMO | 原生场景，但采购与合规周期长，不作首单 |
| 内部 Champion | 客户方空间数据/BI 分析师 | 日常使用者与续费影响者 |

## 三、核心洞察：把限制变成功能

这是 v2 与 v1 最本质的区别。逐条对应审查发现的问题：

| 硬伤 / 限制 | 变成什么功能 |
|---|---|
| τ=−2 显著、平行趋势不完美 | **结论强度自动评级器**：输入前趋势 t 值与量级比 → 输出 A/B/C 级 + 触发的止损条件 |
| 合并环敏感性没跑 | **敏感性诊断面板**：明示"此项未校验"，并给出补跑入口与预期产出（诚实优于假装） |
| `bank_closed_rate` 目标泄漏 | **泄漏自检器**：标注每个特征的"信息时点"，凡使用全期聚合的特征一律标红并给出**保守版本**（剔除该特征重算） |
| 2016+ 系数退化、无法预测未来 | **适用域守门**：year > 2015 直接拒绝打分并说明原因——这是护栏，不是 bug |
| 无 out-of-time 验证 | 模型卡上强制显示"随机划分，非时序外推验证"，并标注测试集事件率与真实事件率的差异 |
| 数据免费、结论可复制 | **可复现性体检**：把"能不能复现"做成可验收清单（版本锁、指纹、相对路径、产物入库率） |

**一句话**：v1 把限制写进"免责声明"，v2 把限制写成**会自动触发的产品行为**。

## 四、功能架构：四个模块（输入 → 计算 → 输出）

### 模块 1 · 数据准入体检（Go / No-Go Intake）—— **产品首页，第一入口**

> 定位：不需要任何客户数据就能产生可交付输出，是获客入口，也是唯一不受方法论硬伤影响的模块。

**输入**（一页纸问卷，6 题）
稳定实体 ID / 坐标缺失率 / 结果变量层级 / 时间跨度 / 事件可定义性与外生性 / 样本量

**计算**
- 6 条 Go/No-Go 规则（`商业化文档 §4.5`）
- **外生性打分**：关店是并购驱动（外生，可冲 A/B 级）还是自主决策（内生，降级 C 级）
- 工期估算：分层难度模型（展示 1 周 / 工程 1–2 周 / 空间 1–2 周 / 识别 2–4 周 / 数据 3–6 周）
- 若用户上传样本数据 → **真实调用 datakit** 跑 `scan → profile → validate`，自动复算本项目踩过的三个坑

**输出（可交付）**
- 可行性评级卡 A / B / C + 预计工期区间 + 补数清单 + 报价档位提示
- 导出：可打印《数据可行性评估书》+ JSON

---

### 模块 2 · 冲击评估器（Impact Estimator）

> 对应 `project1`。**必须在修补 Q2 之后上线**（见 §六 P0-1）。

**输入**
暴露强度（5 km 内同业关闭事件数，滑块区间需补描述统计）/ 期初业绩对数 / 网点数 / 事件后年数 τ(0–4) / 事件年份 / 环口径

**计算（全部用入库的真实系数）**
- 时间维度：`event_study.table[]`（τ=−3…+4，含 SE 与 p）
- 网点级：`twfe.params` → `Δ = −0.052594 + 0.013823 × strength`
- 空间分解：`slx.params.treat_strength`（本地 −0.0059）与 `W_treat_strength`（邻域 +0.0090）
- 置信度折扣：`sensitivity.coordinate_precision.top_precision_pct_by_era`

**输出**
- 逐年影响曲线（带 ±1.96·SE 带）+ 本地/邻域分解
- **强制显示"均值强度处的边际效应"**（修补 Q2 的外推问题）
- 自动盖章结论强度等级 + 触发中的止损条件
- 导出：打印 PDF + JSON（含所用系数的文件路径，可审计）

**护栏（不可关闭）**
用户一旦勾选"用于 ROI 测算"或"对外因果声明" → 立即弹红色停止，引用止损条件原文。

### 模块 3 · 风险归因台（Risk Attribution）—— **改名，不再叫"风险预测"**

> 对应 `project2`。审查 Q6 已证明它**预测不了未来**，叫"预测"是虚标。

**定位修正**：历史归因 + 情景分析，不是预测。

**输入**
`bank_closed_rate` / `log_depsumbr` / `neighbor_count` / `age` / `lat` / `lng` / `year`(1995–2015) / `BKCLASS` / `fragility_tier`
滑块区间全部来自 `02_profile/output/profile.yaml` 与 `05_map/output/map.md` 的真实分布

**计算**
`cloglog_summary.txt` 完整系数表 → η = Xβ → `p = 1 − exp(−exp(η))`
- 逐因子贡献瀑布（`base_value = −4.1643`，来自 `shap_force.json`）
- **保守版本**：剔除 `bank_closed_rate`（泄漏特征）后重算，与全特征版本并列展示

**输出**
- 风险归因卡 + 因子贡献 + 保守/全特征双版本对比
- 模型体检条（AUC 0.8814 / C-index 0.8096 / Brier 0.1609 + **标注"随机划分、测试集事件率 13.78% ≠ 真实 4.13%"**）
- **适用域守门**：year > 2015 拒绝打分并解释

**上线前置**：必须先做 P0-3（泄漏修补 + out-of-time 验证）。在此之前该模块**保持关闭**并明示原因。

### 模块 4 · 口径实验室（Caliber Lab）

> 对应 `project6`。**唯一没有硬伤、可立即上线的模块**。

**输入**：数据集（4 个）× 空间权重（Queen / KNN k=4 / k=8）× 格值尺度（原始 / log1p）× 环口径（求和 / 密度）

**计算**：`05_map/output/<ds>/ladder_report.json` ×4 的 L0–L3 实测值

**输出**：换定义 → 结论怎么变的实时对比（Moran's I 0.0132 ~ 0.7077）+ 可复现清单

**合规提示**：明示 SNAP 两数据集禁商用、商用版只剩 fdic + sz_bike（修正"4 数据集"的规模叙事）

## 五、技术形态建议

### 5.1 双形态（默认纯静态，可选本地服务）

| 形态 | 启动方式 | 能力 | 何时用 |
|---|---|---|---|
| **A · 静态**（默认，必须可用） | 双击 `index.html` | 模块 1/2/4 全部 + 模块 3（在 P0 修补后）；所有计算用入库系数在浏览器内完成 | 交付、演示、离线评审 |

形态 B 不启动时，上传功能显示"需启动本地服务"并给出命令，**不假装能用**。

### 5.2 为什么不做完整前后端

- 商业化文档已判定自助 SaaS（M4）"启动成本很高，暂缓"；
- 首单是项目制（M1/M2），不需要多租户与计费；
- 合规红线要求"数据由客户提供、我们不持有与转售" → **不做持久化存储反而是合规优势**。

### 5.3 分层（沿用并强化 v1 的好设计）

| 层 | 文件 | 规则 |
|---|---|---|
| 事实层 | `data/portal_data.js`（`build_data.py` 生成） | **禁止手改**；缺失置 `null` |
| 叙事层 | `data/content.js` | 手写，**不含任何数字** |
| 计算层 | `assets/engines.js`（新增） | 纯函数，可单测 |
| 表现层 | `assets/app.js`、`charts.js`、`style.css` | — |

**新增**：计算层独立成 `engines.js` 并配 `tests/`（node 原生断言），因为这是唯一会"算错"的地方。

## 九、需要你拍板的问题（信息缺口收敛版）

### A. 决定产品形态（阻塞，必须答）
1. **P0 六条是否授权修改既有文件 / 重跑管线？** 这决定了模块 2/3 能否上线。
2. **目标市场国内还是海外？** 国内拿不到网点级业绩 → 模块 2 整体降级为描述性；海外有 FCA/LINK 等替代数据源。
3. **部署形态是 M1（我们跑管线出报告）还是 M4（客户自助上传）？** 决定要不要做上传与任务队列。

### B. 决定商业叙事（重要）
4. **有没有任何真实客户线索？**（哪怕 1 次访谈 / 1 个 POC 意向）没有的话，"商业化设计"必须改称"商业化假设"。
5. **project3 / project4 / project5 去哪了？** 汇报稿里"我们/管理层/XX 人日"的语境是什么？这关系到"独立开发"能否成立。

### C. 决定细节
6. 交付物格式：PDF 报告 / Excel 名单 / API？有没有客户模板（白标要求）？
7. 是否需要地图底图？（Kepler 需 token + 联网，国内涉及测绘资质）
8. 是否需要中英双语？（`fragility_tier` 取值本身是中文字符串，国际化需重构枚举）
